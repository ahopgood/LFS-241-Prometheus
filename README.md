## Lab 5.2 Selecting Series
* A metric can have multiple series
  * `demo_api_request_duration_seconds_count` is a metric
* A series models a sub-set of a metric based on a combination of different labels
  * `demo_api_request_duration_seconds_count{instance="demo1:8080", job="demo", method="GET", path="/api/bar", status="200"}`
  * This series models the `instance` that generated the metric, the `job` associated with it, the `method`, `path` and `status` of the HTTP request
* Best practise is to always select by job `{job="demo"}` 
  * The same metric name may be generated by another job with different semantics or labels

## Lab 5.3 Computing Rates of Increase
* Counter metrics only ever go up
* Typically we want to know **how fast** a counter is increasing
* `rate()` calculates the _per second_ increase of a counter, _averaged_ over a window
* It is smoother than `irate` and so better used for alerting expressions
```
rate(demo_api_request_duration_seconds_count{job="demo"}[5m])
```
* `irate()` - instantaneous rate only considers the _last two_ data points and calculates a rate from them
  * `irate` reacts faster to counter changes, useful for high-resolution, zoomed in graphs
* `increase()` provides the _total increase_ over a given time window

> Sticking to `rate()` and per-second units everywhere is best for making comparisons and arithmetics between expressions

## Lab 5.4 Computing Derivatives
* Gauge metrics track a value that can go _up_ or _down_ e.g. temperatures or hard disk space
* Counters can only increase
* Use `delta()` and `deriv()` for gauges
* `delta()` only considers the _first_ and _last_ data point under the provided time window
  * It will disregard trends in-between the data points
* Obtain the increase in disk usage over 15 minutes
```
delta(demo_disk_usage_bytes{job="demo"}[15m])
```
* `deriv()` provides the _per-second_ derivative over the same time window
  * Uses full linear regression over all data points 
* Calculate how much the disk usage is going up or down per-second within a 15 minute window
```
deriv(demo_disk_usage_bytes{job="demo"}[15m])
```
* `predict_linear()` allows you to predict what the value of a gauge will be in a given amount of time in the future
* Predict disk usage in an hour
```
predict_linear(demo_disk_usage_bytes{job="demo"}[15m], 3600)
```

## Lab 5.5 Aggregations
Time series data is _highly dimensional_ which is helpful for drilling down.  
But other times you'll want to **aggregate** over dimensions to show overall results.  
* To find the **total** number of requests our demo service is handling _per second_ you can use `sum` to add up the individual rates:
```
sum(rate(demo_api_request_duration_seconds_count{job="demo"}[5m]))
```
  * On its own the rate will display multiple dimensions: path, method, status and instance
  * Sum will aggregate these into a single series.
* How can we _preserve_ some of the dimensions and aggregate those we don't care about?
* `without()` will allow us to exclude certain fields from the series and to aggregate by them
```
sum without(method, status) (rate(demo_api_request_duration_seconds_count{job="demo"}[5m]))
```
* `by()` is the opposite and will include the labels specified in the output series
```
sum by(instance, path, job) (rate(demo_api_request_duration_seconds_count{job="demo"}[5m]))
```
* Use whichever requires the least modification

### Aggregation operators
These aggregators all support `without()` and `by()`

* `sum()` calculate the sum over dimensions
* `min()` select the minimum value across dimensions
* `max()` select the maximum value across dimensions
* `avg()` calculate the average over dimensions
* `stddev()` calculate the population standard deviation over dimensions
* `stdvar()` calculate the population standard variance over dimensions
* `count()` count the number of series in a vector
* `count_values(value_label, ...)` counts the number of series for each **distinct** sample value
* `bottomk(k, ...)` selects the smallest k elements by sample value
* `top(k, ...)` selects the smallest k elements by sample value
* `quantile(phi, ...)` calculates the phi-quantile (O =< phi =< 1) over dimensions

## Lab 5.6 Arithmetic
* Basic arithmetic is supported: `(2 + 3 / 6) * 2^2`
* You can multiply a vector (list) by a scalar (number)
* If you wanted to display a byte value as GiB instead you can do:
```
demo_batch_last_run_processed_bytes{job="demo"} / 1024^3
```
* Scalar operations are applied to _every element_ (series) in the vector
* [Binary Operators documentation](https://prometheus.io/docs/prometheus/latest/querying/operators/#binary-operators)
* You can do arithmetic _between vectors_ (across time series)
  * Prometheus will match series with **identical** label sets on both sides of the operation
* Common example is to calculate the average HTTP response time from a histogram's `_count` series (total number of requests) and `_sum` series (total time spent in requests):
  * This preserves _all_ dimensions in the output 
  * The only difference between the two series is the metric name
```
rate(demo_api_request_duration_seconds_count{job="demo"}[5m])
/
rate(demo_api_request_duration_seconds_sum{job="demo"}[5m])
```
* What if all dimensions don't match?
* Trying to calculate the ratio errors vs total rate of all requests (will be a number between 0 and 1):
```
sum without(status)
(rate(demo_api_request_duration_seconds_count{job="demo",status="500"}[5m]))
/
sum without(status)
(rate(demo_api_request_duration_seconds_count{job="demo"}[5m]))
```
* We can aggregate away the labels that one series doesn't have
  * We do `without(status)` **BUT** we add the `status="500"` dimension to the series where it exists
  * Why won't the following work?
  ```
  rate(demo_api_request_duration_seconds_count{job="demo", status="500"}[5m])
  /
  rate(demo_api_request_duration_seconds_count{job="demo" }[5m])
  ```
    * The left hand operator is evaluated first and its dimensions must be consistent
    * Because the right hand `demo_api_request_duration_seconds_count` doesn't match the left hand dimension it would be dropped from the output
    * It is equivalent to `rate(demo_api_request_duration_seconds_count{job="demo", status!="500"} [5m])` which makes the mismatch clearer
    * We're selecting `status="500"` on the left and the right value `status!="500"` doesn't match 

### Vector matching
* [Vector matching documentation](https://prometheus.io/docs/prometheus/latest/querying/operators/#vector-matching)
* What if one has more dimensions than the other but we want to reflect it in the mapping?
  * `demo_num_cpus` tells you the number of cores
  * `demo_cpu_usage_seconds_total` has a `mode` label that splits the CPU usage into `idle`, `system`, `user`
  * We want per-mode CPU usage divided by the number of cores, we tell the division operator to _group_ its results by the extra `mode` label
  * Use the `on()` operator to select `job, instance`, thereby excluding `mode`
  * `ignoring()` is the opposite of `on()` 
  * Then use the `group_left` modifier to map the data from the series on the right onto the series on the left
  ```
  rate(demo_cpu_usage_seconds_total{job="demo"}[5m])
  / on(job, instance) group_left
  demo_num_cpus{job="demo"}
  ```
  * e.g `idle` rate is at 2.0, normalised over 4 CPU cores would become `0.5`
  * If there are more dimensions on the right then we use `group_right`

## Lab 7.3 Explore Node Exporter Metrics
* [http://localhost:9100/metrics](http://localhost:9100/metrics) for all node metrics
### CPU
* `node_cpu_seconds_total` tracks how many seconds have been uses since boot time _per core_ (label `cpu`) and _per mode_ (label `mode`)
  * Other labels include `instance` (host) and `job`
  * Modes are `idle`, `iowait`, `irq`, `nice`,`softirq`, `steal`, `system`, `user`
```
rate(node_cpu_seconds_total{job="node"}[1m])
```
* To see actual CPU usage we'll filter out `idle` mode:
```
sum without(cpu) (rate(node_cpu_seconds_total{mode!="idle",job="node"}[1m]))
```
  * `mode!="idle"` removes the idle mode
  * `sum (without(cpu))` gives us usage over **all** CPU cores by excluding the `cpu` label

### Memory
* Memory is made of "free", "buffers" and "cached" memory:
```
(
  node_memory_MemFree_bytes{job="node"}
  + 
  node_memory_Buffers_bytes{job="node"}
  +
  node_memory_Cached_bytes{job="node"}
) / 1024^3
```
* All three metrics are gauges
* We then divide by `1024^3` to convert bytes into GB (Kilobytes > Megabytes > Gigabytes).

### Filesystem
* `node_filesystem_free_bytes` shows the free bytes on a filesystem
* `node_filesystem_free_bytes` will tell you how many bytes in total the filesystem has
* Together we can calculate filesystem usage:
```
(
  node_filesystem_free_bytes
  /
  node_filesystem_size_bytes
) * 100
```
* Can we see this usage over time?
  * Both metrics are gauges

### Network
* To see incoming and outgoing network traffic, grouped by network interface:
```
rate(node_network_receive_bytes_total[1m])
+
rate(node_network_transmit_bytes_total[1m])
```
* Both metrics are counters

### Other metrics
* `node_boot_time_seconds` - system's boot time as a unix timestamp
  * `changes(node_boot_time_seconds[30m]) > 3` check for nodes that reboot frequently; 3 reboots in the last 30 minutes
* `node_time_seconds` - current system time
  * `node_time_seconds - timestamp(node_time_seconds)` compare prometheus' time to that of a scraped node
  * `timestamp` gets the **scrape** timestamp of a **sample** node

## Lab 10.1 Studying and Running an Example Exporter
```
mkdir cpu-exporter
```
* Create a file called `cpu_exporter.py`
```python
import time
import psutil

from prometheus_client import start_http_server
from prometheus_client.core import CounterMetricFamily, REGISTRY

class CPUCollector(object):
  def collect(self):
    c = CounterMetricFamily('cpu_exporter_cpu_usage_seconds_total', 'The total number of CPU seconds used per mode.', labels=['mode']) 
    for mode, usage_seconds in psutil.cpu_times()._asdict().items():
      c.add_metric([mode], usage_seconds)
    yield c

REGISTRY.register(CPUCollector())

if __name__ == '__main__':
  start_http_server(8000)
  while True:
    time.sleep(1)
```
* The server is started on port `8000`
* It calls `collect()` on the `CPUCollector` class _once per scrape_
* The `psutil` library is used to fetch the current CPU usage
* A `CounterMetricFamily` is used to translate the usage into a "throw away" Prometheus metrics family
* A metrics family is a group of series with the same metric name but different labels

Create a Dockerfile to package up the custom exporter
```dockerfile
FROM docker.io/python:3.13
WORKDIR /usr/src/cpu-exporter/
RUN pip install --no-cache-dir prometheus_client psutil
COPY ./cpu_exporter.py .
EXPOSE 8000
CMD ["python","cpu_exporter.py"]
```
* Build `docker build -t cpu-exporter .`
* Run as a container in the lab network:
```

  --name cpu-exporter \
  -h cpu-exporter \

```

## Lab 11.1 Histograms and Calculating Quantiles
* Prometheus v2.40 and above support ["native histograms"](https://prometheus.io/docs/specs/native_histograms/) which:
  * do not require configuration of bucket boundaries during instrumentation
  * reduce the cost of empty buckets
* We're using classic histograms here
[* A histogram gives you an idea of:
  * the **distribution** of request durations
  * how many of your **requests take longer than x ms**](https://prometheus.io/docs/practices/histograms/#errors-of-quantile-estimation)
* To calculate _quantiles_ (e.g. 99th percentile) you need `histogram_quantile()`
  * First parameter is a number between `0` and `1` 
  * Second parameter is a histogram
  * Take the `rate()` of the histogram otherwise you get a quantile over the **entire lifetime** of the bucket counters
```
histogram_quantile(0.9, rate(demo_api_request_duration_seconds_bucket{job="demo"}[5m]))
```
* To see overall system latency you can aggregate away some labels
  * Don't aggregate away the `le` label as it is required
```
histogram_quantile(
  0.9,
  sum without(status, method) (
    rate(demo_api_request_duration_seconds_bucket{job="demo"}[5m])
  )
)
```

## Lab 11.2 Filtering by Sample Value
We can select series by their metric name and label values, we can also filter by sample value as well.  
### Time Series against a scalar
You can apply a binary comparison between a time series vector and a scalar number.  
A use case is thresholds in alerting expressions:
* Only `500` errors above 0.2 per second:
```
rate(demo_api_request_duration_seconds_count{status="500",job="demo"}[5m]) > 0.2
```
* Works for all comparison operators: `<`, `<=`, `>=`, `!=`, `==`

### Time Series against Time Series
Select all `500` statuses that are `x50` larger than the _total_ traffic, for a given path, method and instance:
```
rate(demo_api_request_duration_seconds_count{status="500",job="demo"}[5m]) * 50
> ignoring(status)
  sum without(status)
(rate(demo_api_request_duration_seconds_count{job="demo"}[5m]))
```
* Why use a `sum without()` on the right hand expression?
  * We need to aggregate the results and then strip out status
* Why **don't** we need it on the left expression?
  * Because we're already filtering by status to include only `500`
* Why use the `ignoring()` clause?
  * This ensures series on the left **and** right are matched on all of their labels except status
  * Without this clause the left hand side series would still contain `status=500` and won't match
  * This also means that any series with an unmatched label is dropped

## Lab 11.3 Performing Set Operations
* Correlating two series based on the _mutual_ presence of labels
* `and`, `or`, `unless` are set operators

### And
* `and` performs set **intersection**, it allows you to select only a series in a vector that have the same labels in a second vector 
* Graph the status `500` error rates 
  * **only** for those whose `path`, `method` and `instance` combinations 
  * have a request rate _larger_ than 10 per second
```
sum without(status)
(rate(demo_api_request_duration_seconds_count{job="demo",status="500"}[5m]))
and
sum without(status)
(rate(demo_api_request_duration_seconds_count{job="demo"}[5m])) > 10
```
* Filter by status on the left expression
* Aggregate and then exclude the status from _both_ so we can perform operations
* Use `and` to leave just `path`, `method` and `instance` series

### Or
* `or` performs set **union** and allows you to select label sets from two series that are in **either** of the two vectors
* Each sample will be taken from the left-hand side if present
* Will use the right hand if not present
* Useful for when you're missing label combinations in one vector and want to fill them in with values from another vector

Use case, we want the `500` status rate for **all paths** that have _ever_ received HTTP requests.
* No series exist for endpoints that haven't received a `500`
* Using or allows us to fill in the labels from the total request count to the empty series
```
sum by(path)
(rate(demo_api_request_duration_seconds_count{job="demo",status="500"}[5m]))
or
sum by(path) (rate(demo_api_request_duration_seconds_count{job="demo"}[5m])) *
0
```
* We will now see the `500` error rate for the `/api/nonexistent` path which only typically returns `404`

### Unless
* `unless` performs set **complement** will only propagate labels from one vector into another if they are **not** found in the second vector

## Lab 11.4 Working with Timestamp Metrics
Some services and exporters will encode a timestamp into the **sample value** of a metric (note, not a label).  
The demo service exposes the last successful run of a batch job
```
demo_batch_last_success_timestamp_seconds{job="demo"}
```
This produces a staircase graph, typically though you want to calculate a _duration_:
```
time() - demo_batch_last_success_timestamp_seconds{job="demo"}
```
It can then be combined with a threshold to detect jobs that have not finished in the last 1.5 minutes (90 seconds):
```
time() - demo_batch_last_success_timestamp_seconds{job="demo"} > 1.5 * 60
```

## Lab 11.5 Offsetting Data
Offsetting allows you to compare current system data with behaviour from the past.  

```
rate(demo_api_request_duration_seconds_count{job="demo"}[5m] offset 1h)
```
Calculate a ratio between the current rate and the one an hour ago
```
rate(demo_api_request_duration_seconds_count{job="demo"}[5m])
/
rate(demo_api_request_duration_seconds_count{job="demo"}[5m] offset 1h)
```

In the table view it can be useful to sort query results, it has no impact on graphs

```
sort_desc(sum by(path) (rate(demo_api_request_duration_seconds_count{job="demo"}[5m])))
```

## Lab 11.7 Inspecting Scrape Health
When prometheus cannot scrape a target it records this in a metric:
```
up{job="demo"}
```
* It is binary 1 - up, 0 - down
```
up{job="demo"} == 0
```
If you wanted to alert when half of all demo services are down:
```
count by(job) (up{job="demo"} == 0)
/
count by(job) (up{job="demo"})
> 0.5
```
  * A simpler version is `1 - avg by(job) (up{job="demo"}) > 0.5`

## Lab 13.1 Setting Up Consul-Based Discovery
Prometheus has native support for [Consul](https://developer.hashicorp.com/consul) service discovery.  
Create a configuration file `demo-service.json`, this will define each of our demo services:
  * worth noting when using docker compose to deploy you'll want the hostname to match, e.g. demo1, demo2, demo3 not d1, d2, d3
```json
{
  "services": [
    {
      "id": "demo1",
      "name": "demo",
      "address": "d1",
      "port": 8080
    },
    {
      "id": "demo2",
      "name": "demo",
      "address": "d2",
      "port": 8080
    },
    {
      "id": "demo3",
      "name": "demo",
      "address": "d3",
      "port": 8080
    }
  ]
}
```
Next start consul in development mode, providing our configuration file from above:
```
docker run -d --net lab --name consul -h consul \
  -v ./demo-service.json:/etc/consul/demo-service.json \
  docker.io/hashicorp/consul:1.20 \
  agent -bind=0.0.0.0 -client=0.0.0.0 -dev \
  -config-file=/etc/consul/demo-service.json
```
Consul also registers itself as a target.  

To make Prometheus discover the demo service targets from Consul we add the following scrape file:
```
cat <<EOF >> ~/prometheus/prometheus.yml
  - job_name: 'consul-sd-demo'
    consul_sd_configs:
      - server: 'consul:8500'
    relabel_configs:
      - action: keep
        source_labels: [__meta_consul_service]
        regex: demo
EOF
```
* We're using **relabelling** here to exclude the consul service as it doesn't have `/metrics` endpoint 
* Now consul should show as a scrape target
* Use `{job="consul-sd-demo"}` as a query to discover the demo service metrics 


## Lab 13.2 Configuring File-Based Discovery
[`file_sd`discovery mechanism](https://prometheus.io/docs/prometheus/latest/configuratian/configuration/#file_sd_config)  documentation.
Add a scrape config to Prometheus to read the `targets.yml` file:
```
cat <<EOF >> ~/prometheus/prometheus.yml
  - job_name: 'file-sd-demo'
    file_sd_configs:
      - files:
        - 'targets.yml'
EOF
```
Add a new file `targets.yml` in the same directory as your `prometheus.yml` (either to the volume directory or a direct named file volume)
```
- targets:
    - 'd1:8080'
    - 'd2:8080'

    env: production
- targets:
    - 'd3:8080'

    env: staging
```

* Prometheus will watch the file and update the scrape when you make changes
  * When making updates in production make sure to do so **atomically** so that _partial_ updates don't happen
  * Do this by making changes to a _copy_ of the file and then `mv/cp` it to the directory prometheus is watching

## Lab 14.1 Set Up Blackbox Exporter
[Blackbox exporter docs](https://github.com/prometheus/blackbox_exporter/blob/master/README.md)

A target has the following relabelling applied:
* Target address -copied-to-> `__param_target`
* `__param_target` -copied-to-> `instance`  
* `__address__` -updated-to-> the blackbox exporter IP

```
__address__ myservice.com
__param_target nil
instance myservice1
```
Becomes
```
__address__ blackbox-exporter:9115
__param_target myservice.com
instance myservice.com
```

Create the `blackbox.yml` configuration file:
```
cat <<EOF >> ~/blackbox.yml
  modules:
    http_2xx:
      prober: http
      timeout: 2s
      http:
        method: GET
```
Start the blackbox exporter:
```
docker run -d --net lab --name blackbox-exporter -h bb-exporter \
-p 9115:9115 -v ~/blackbox.yml:/config/blackbox.yml \
docker.io/prom/blackbox-exporter:v0.26.0 \
--config.file=/config/blackbox.yml
```
You can see the blackbox exporter output by pointing it at prometheus.io
Try heading to
[http://localhost:9115/probe?target=https://prometheus.io&module=http_2xx](http://localhost:9115/probe?target=https://prometheus.io&module=http_2xx)

## Lab 14.2 Probing Example Services
Add the blackbox exporter scrape config to your `prometheus.yaml`:
```yaml
cat <<EOF >> ~/prometheus/prometheus.yml
  - job_name: 'blackbox'
    metrics_path: /probe
    params:
      module:
        - http_2xx # Look for an HTTP 200 response.
    static_configs:
      - targets: # Targets to probe through the Blackbox Exporter.
        - 'http://prometheus.io'
        - 'https://prometheus.io'
        - 'http://example.com:8080'
    relabel_configs:
      - source_labels: [__address__]
        target_label: __param_target
      - source_labels: [__param_target]
        target_label: instance
      - target_label: __address__
        replacement: blackbox-exporter:9115 # Blackbox Exporter address.
EOF
```
With this in place prometheus should start scraping the blackbox exporter, you should see it under [http://localhost:9091/targets](http://localhost:9091/targets)
* Probe targets will all show as `UP` but that doesn't mean the probes succeeded
* It means the scrape succeeded

The `http` prober module has several metrics:
* `probe_duration_seconds` - how many seconds the backend probe took
* `probe_success` - if the probe was successful (0 failure or 1 success)
* `probe_http_status_code` - the backend's HTTP status
* `probe_http_content_length` - the length in byte of the backend HTTP response content
* `probe_http_redirects` - how many redirects were followed
* `probe_http_ssl` - whether the probe used SSL in the final redirect (0 or 1)
* `probe_ssl_earliest_cert_expiry` - for an SSL request, what is the timestamp of the certificate expiry
* `probe_ip_protocol` - IP protocol version used for the probe (4 or 6)

You can see the probe results with the following query:
```
probe_success{job="blackbox"}
```
This should show:
```
probe_success{instance="http://prometheus.io", job="blackbox"}	1
probe_success{instance="https://prometheus.io", job="blackbox"}	1
probe_success{instance="http://example.com:8080", job="blackbox"}	0
```

You can find out how many days until the [https://promoetheus.io](https://prometheus.io) SSL certificate expires:
```
(
probe_ssl_earliest_cert_expiry{instance="https://prometheus.io"}
-
time()
) / 86400
```
* This sort of expression is useful for alerting on expiring certificates

## Lab 15.3 Pushing Metrics From a Batch Job
We're going to simulate a batch job with curl
```
cat <<EOF | curl --data-binary @- http://localhost:9091/metrics/job/demo_batch_job
# TYPE demo_batch_job_last_successful_run_timestamp_seconds gauge
# HELP demo_batch_job_last_successful_run_timestamp_seconds The Unix timestamp in seconds of the last successful batch job run. 
demo_batch_job_last_successful_run_timestamp_seconds $(date +%s)
# TYPE demo_batch_job_last_run_timestamp_seconds gauge
# HELP demo_batch_job_last_run_timestamp_seconds The Unix timestamp in seconds of the last successful batch job run. 
demo_batch_job_last_run_timestamp_seconds $(date +%s)
# TYPE demo_batch_job_users_deleted gauge
# HELP demo_batch_job_users_deleted How many users were deleted in the last batch job run.
demo_batch_job_users_deleted $RANDOM
EOF
```
* We're using `$(date +%s)` to generate timestamps
* The `$RANDOM` shell var is being used to generate a number between 0 and 32767 for the number of deleted users 
* You may need to regenerate the random var with `echo $RANDOM` before sending the next request

After running visit the pushgateway [http://localhost:9091/metrics](http://localhost:9091/metrics) to view the metrics
* Run a few more times to see the metrics change
