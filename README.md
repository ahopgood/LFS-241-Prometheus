* Grab the prometheus image and run as a container
```
docker create --name config docker.io/prom/prometheus:v3.2.1
```

```
mkdir ~/prometheus && cd ~/prometheus
```

```
docker cp config:/etc/prometheus/prometheus.yml .
```
* Remove the container
```
docker rm config
```

```
docker run --rm docker.io/prom/prometheus:v3.2.1 -h
```

* The `Graph` tab plots values over time

Prometheus exposes itself as a scrape target so you can query for it:
* `prometheus_tsdb_head_samples_appended_total` the total number of samples ingested into prometheus's local storage
* `rate(prometheus_tsdb_head_samples_appended_total[1m])` the number of samples ingested per second as _averaged_ over a 1-minute window
* `up{job="prometheus"}` value of the **synthetic** `up` metric for prometheus which is set to 0 when a scrape fails and 1 when successful.

## Lab 5.2 Selecting Series
* A metric can have multiple series
  * `demo_api_request_duration_seconds_count` is a metric
* A series models a sub-set of a metric based on a combination of different labels
  * `demo_api_request_duration_seconds_count{instance="demo1:8080", job="demo", method="GET", path="/api/bar", status="200"}`
  * This series models the `instance` that generated the metric, the `job` associated with it, the `method`, `path` and `status` of the HTTP request
* Best practise is to always select by job `{job="demo"}` 
  * The same metric name may be generated by another job with different semantics or labels

## Lab 5.3 Computing Rates of Increase
* Counter metrics only ever go up
* Typically we want to know **how fast** a counter is increasing
* `rate()` calculates the _per second_ increase of a counter, _averaged_ over a window
* It is smoother than `irate` and so better used for alerting expressions
```
rate(demo_api_request_duration_seconds_count{job="demo"}[5m])
```
* `irate()` - instantaneous rate only considers the _last two_ data points and calculates a rate from them
  * `irate` reacts faster to counter changes, useful for high-resolution, zoomed in graphs
* `increase()` provides the _total increase_ over a given time window

> Sticking to `rate()` and per-second units everywhere is best for making comparisons and arithmetics between expressions

## Lab 5.4 Computing Derivatives
* Gauge metrics track a value that can go _up_ or _down_ e.g. temperatures or hard disk space
* Counters can only increase
* Use `delta()` and `deriv()` for gauges
* `delta()` only considers the _first_ and _last_ data point under the provided time window
  * It will disregard trends in-between the data points
* Obtain the increase in disk usage over 15 minutes
```
delta(demo_disk_usage_bytes{job="demo"}[15m])
```
* `deriv()` provides the _per-second_ derivative over the same time window
  * Uses full linear regression over all data points 
* Calculate how much the disk usage is going up or down per-second within a 15 minute window
```
deriv(demo_disk_usage_bytes{job="demo"}[15m])
```
* `predict_linear()` allows you to predict what the value of a gauge will be in a given amount of time in the future
* Predict disk usage in an hour
```
predict_linear(demo_disk_usage_bytes{job="demo"}[15m], 3600)
```

## Lab 5.5 Aggregations
Time series data is _highly dimensional_ which is helpful for drilling down.  
But other times you'll want to **aggregate** over dimensions to show overall results.  
* To find the **total** number of requests our demo service is handling _per second_ you can use `sum` to add up the individual rates:
```
sum(rate(demo_api_request_duration_seconds_count{job="demo"}[5m]))
```
  * On its own the rate will display multiple dimensions: path, method, status and instance
  * Sum will aggregate these into a single series.
* How can we _preserve_ some of the dimensions and aggregate those we don't care about?
* `without()` will allow us to exclude certain fields from the series and to aggregate by them
```
sum without(method, status) (rate(demo_api_request_duration_seconds_count{job="demo"}[5m]))
```
* `by()` is the opposite and will include the labels specified in the output series
```
sum by(instance, path, job) (rate(demo_api_request_duration_seconds_count{job="demo"}[5m]))
```
* Use whichever requires the least modification

### Aggregation operators
These aggregators all support `without()` and `by()`

* `sum()` calculate the sum over dimensions
* `min()` select the minimum value across dimensions
* `max()` select the maximum value across dimensions
* `avg()` calculate the average over dimensions
* `stddev()` calculate the population standard deviation over dimensions
* `stdvar()` calculate the population standard variance over dimensions
* `count()` count the number of series in a vector
* `count_values(value_label, ...)` counts the number of series for each **distinct** sample value
* `bottomk(k, ...)` selects the smallest k elements by sample value
* `top(k, ...)` selects the smallest k elements by sample value
* `quantile(phi, ...)` calculates the phi-quantile (O =< phi =< 1) over dimensions

## Lab 5.6 Arithmetic
* Basic arithmetic is supported: `(2 + 3 / 6) * 2^2`
* You can multiply a vector (list) by a scalar (number)
* If you wanted to display a byte value as GiB instead you can do:
```
demo_batch_last_run_processed_bytes{job="demo"} / 1024^3
```
* Scalar operations are applied to _every element_ (series) in the vector
* [Binary Operators documentation](https://prometheus.io/docs/prometheus/latest/querying/operators/#binary-operators)
* You can do arithmetic _between vectors_ (across time series)
  * Prometheus will match series with **identical** label sets on both sides of the operation
* Common example is to calculate the average HTTP response time from a histogram's `_count` series (total number of requests) and `_sum` series (total time spent in requests):
  * This preserves _all_ dimensions in the output 
  * The only difference between the two series is the metric name
```
rate(demo_api_request_duration_seconds_count{job="demo"}[5m])
/
rate(demo_api_request_duration_seconds_sum{job="demo"}[5m])
```
* What if all dimensions don't match?
* Trying to calculate the ratio errors vs total rate of all requests (will be a number between 0 and 1):
```
sum without(status)
(rate(demo_api_request_duration_seconds_count{job="demo",status="500"}[5m]))
/
sum without(status)
(rate(demo_api_request_duration_seconds_count{job="demo"}[5m]))
```
* We can aggregate away the labels that one series doesn't have
  * We do `without(status)` **BUT** we add the `status="500"` dimension to the series where it exists
  * Why won't the following work?
  ```
  rate(demo_api_request_duration_seconds_count{job="demo", status="500"}[5m])
  /
  rate(demo_api_request_duration_seconds_count{job="demo" }[5m])
  ```
    * The left hand operator is evaluated first and its dimensions must be consistent
    * Because the right hand `demo_api_request_duration_seconds_count` doesn't match the left hand dimension it would be dropped from the output
    * It is equivalent to `rate(demo_api_request_duration_seconds_count{job="demo", status!="500"} [5m])` which makes the mismatch clearer
    * We're selecting `status="500"` on the left and the right value `status!="500"` doesn't match 

### Vector matching
* [Vector matching documentation](https://prometheus.io/docs/prometheus/latest/querying/operators/#vector-matching)
* What if one has more dimensions than the other but we want to reflect it in the mapping?
  * `demo_num_cpus` tells you the number of cores
  * `demo_cpu_usage_seconds_total` has a `mode` label that splits the CPU usage into `idle`, `system`, `user`
  * We want per-mode CPU usage divided by the number of cores, we tell the division operator to _group_ its results by the extra `mode` label
  * Use the `on()` operator to select `job, instance`, thereby excluding `mode`
  * `ignoring()` is the opposite of `on()` 
  * Then use the `group_left` modifier to map the data from the series on the right onto the series on the left
  ```
  rate(demo_cpu_usage_seconds_total{job="demo"}[5m])
  / on(job, instance) group_left
  demo_num_cpus{job="demo"}
  ```
  * e.g `idle` rate is at 2.0, normalised over 4 CPU cores would become `0.5`
  * If there are more dimensions on the right then we use `group_right`

## Lab 7.3 Explore Node Exporter Metrics
* [http://localhost:9100/metrics](http://localhost:9100/metrics) for all node metrics
### CPU
* `node_cpu_seconds_total` tracks how many seconds have been uses since boot time _per core_ (label `cpu`) and _per mode_ (label `mode`)
  * Other labels include `instance` (host) and `job`
  * Modes are `idle`, `iowait`, `irq`, `nice`,`softirq`, `steal`, `system`, `user`
```
rate(node_cpu_seconds_total{job="node"}[1m])
```
* To see actual CPU usage we'll filter out `idle` mode:
```
sum without(cpu) (rate(node_cpu_seconds_total{mode!="idle",job="node"}[1m]))
```
  * `mode!="idle"` removes the idle mode
  * `sum (without(cpu))` gives us usage over **all** CPU cores by excluding the `cpu` label

### Memory
* Memory is made of "free", "buffers" and "cached" memory:
```
(
  node_memory_MemFree_bytes{job="node"}
  + 
  node_memory_Buffers_bytes{job="node"}
  +
  node_memory_Cached_bytes{job="node"}
) / 1024^3
```
* All three metrics are gauges
* We then divide by `1024^3` to convert bytes into GB (Kilobytes > Megabytes > Gigabytes).

### Filesystem
* `node_filesystem_free_bytes` shows the free bytes on a filesystem
* `node_filesystem_free_bytes` will tell you how many bytes in total the filesystem has
* Together we can calculate filesystem usage:
```
(
  node_filesystem_free_bytes
  /
  node_filesystem_size_bytes
) * 100
```
* Can we see this usage over time?
  * Both metrics are gauges

### Network
* To see incoming and outgoing network traffic, grouped by network interface:
```
rate(node_network_receive_bytes_total[1m])
+
rate(node_network_transmit_bytes_total[1m])
```
* Both metrics are counters

### Other metrics
* `node_boot_time_seconds` - system's boot time as a unix timestamp
  * `changes(node_boot_time_seconds[30m]) > 3` check for nodes that reboot frequently; 3 reboots in the last 30 minutes
* `node_time_seconds` - current system time
  * `node_time_seconds - timestamp(node_time_seconds)` compare prometheus' time to that of a scraped node
  * `timestamp` gets the **scrape** timestamp of a **sample** node

## Lab 8.3 Explore Container Metrics
* Per container metrics have the `container` prefix
  * `id` label corresponds to a container's full path name in the host's virtual cgroups fs
    * `/sys/fs/cgroup/docker/7230bbfcad8a1ca963822fb28a06c25df7ba17a801c3c13cf17902
38e53cb630/ `
  * On cgrops v1 the `id` label is different, it has a _per resource_ label
    * `memory`, `cpu`, `pids`
    * `/sys/fs/cgroup/memory/docker/.../ `
  * `image` label - present only when the containers set it
    * e.g. `gcr.io/cadvisor/cadvisor:v0.52.1`
  * `name` label - present only when the containers set it
  * `container_cpu_usage_seconds_total` the number of cpu seconds used by each container, split by core
* Per-second increase rate of CPU usage
```
rate(container_cpu_usage_seconds_total[1m])
```
* Total CPU usage in number of cores for the Grafana container
```
sum without(cpu) (rate(container_cpu_usage_seconds_total{name="grafana"}[1m]))
```
* To get a container's memory usage in bytes
```
container_memory_usage_bytes{name="grafana"}
```
